# 용어집 (Glossary)

> 설계 문서에 등장하는 용어를 이 프로젝트의 맥락과 연결해 정리한다.

## 1. 설계 기법

**이벤트 스토밍 (Event Storming)**
도메인에서 일어나는 사건들을 시간순으로 나열하며 시스템을 설계하는 워크숍 기법. 보통 주황색 포스트잇(이벤트), 파란색(커맨드)을 벽에 붙이며 진행한다. → 우리는 이걸로 서비스 경계와 토픽 설계를 도출했다 (event-design §2).

**도메인 이벤트 (Domain Event)**
비즈니스에서 이미 일어난 사실. 항상 과거형으로 이름 짓는다 — "주문 생성됨(OrderCreated)". 사실이므로 취소할 수 없고, 되돌리려면 반대 사건을 새로 발생시킨다. → 이벤트 카탈로그의 7개 이벤트.

**커맨드 (Command)**
시스템에 "이걸 해달라"고 요청하는 행위. 이벤트와 달리 거절될 수 있다. → "주문 생성", "주문 취소". 커맨드가 성공하면 이벤트가 발행된다.

**정책 (Policy)**
"이벤트 X가 발생하면 커맨드 Y를 실행한다"는 자동 반응 규칙. → "OrderCreated가 발행되면 결제 서비스가 PG 승인을 요청한다".

**애그리거트 (Aggregate)**
항상 한 덩어리로 일관성을 유지해야 하는 객체 묶음과 그 대표(루트). 트랜잭션 하나는 애그리거트 하나만 수정하는 게 원칙. → 주문(orders + order_lines)이 하나의 애그리거트, 재고(inventory)가 또 하나. "재고를 별도 서비스가 아닌 주문 서비스 내부 애그리거트로 시작한다"(ERD §0)는 말은 재고를 독립 배포 단위로 쪼개지 않고 주문 서비스 안의 한 덩어리로 둔다는 뜻.

**상태 머신 (State Machine)**
객체가 가질 수 있는 상태들과 허용된 전이(이동 경로)를 정의한 모델. 핵심 가치는 "허용되지 않은 전이를 거부하는 것". → 주문: CREATED → CONFIRMED / CANCEL_REQUESTED → CANCELLED.

**ADR (Architecture Decision Record)**
아키텍처 결정 하나를 배경·선택지·결정·트레이드오프와 함께 기록한 짧은 문서. "무엇을"이 아니라 "왜"를 남기는 게 목적. → docs/adr/.

**분산 모놀리스 (Distributed Monolith)**
서비스를 쪼개긴 했는데 서로 강하게 엮여서, 모놀리스의 단점(같이 배포해야 함)과 분산 시스템의 단점(네트워크 비용)만 합쳐진 안티패턴. → ADR-0002에서 공유 모듈을 2개로 제한한 이유.

**포트/어댑터 (Port / Adapter, 헥사고날 아키텍처)**
도메인 로직(중심)과 외부 세계(DB, HTTP, Kafka)를 인터페이스(포트)로 분리하고, 구체 기술은 어댑터로 갈아끼우는 구조. → ADR-0001에서 "동기 호출을 이벤트 발행으로 바꿔도 재작업이 어댑터에 한정되는" 근거.

## 2. 분산 트랜잭션

**Saga**
긴 작업을 로컬 트랜잭션의 연쇄로 풀고, 중간 실패 시 앞 단계들을 보상 트랜잭션으로 역순 취소하는 패턴. 이름은 '대하소설'에서 유래 — 긴 이야기를 여러 장(chapter)으로 나누듯이. → 재고 선점 → 결제 → 실패 시 재고 복원 + 주문 취소.

**보상 트랜잭션 (Compensating Transaction)**
이미 커밋된 작업을 "되돌리는 효과를 내는 새로운 작업". 롤백(없던 일로 만들기)이 아니라 상쇄(반대 작업 실행)다. → PaymentFailed 수신 시 재고 복원.

**코레오그래피 vs 오케스트레이션 (Choreography vs Orchestration)**
Saga 진행 방식 두 가지. 코레오그래피(군무) = 지휘자 없이 각 서비스가 이벤트를 보고 알아서 다음 동작 수행. 오케스트레이션(오케스트라) = 지휘자 역할의 중앙 코디네이터가 순서를 통제. → 현재 초안은 코레오그래피, ADR 후보 #7에서 최종 결정.

**2PC (Two-Phase Commit)**
여러 DB를 하나의 트랜잭션으로 묶는 고전 프로토콜. 코디네이터가 전원에게 "준비됐나" 묻고 전원 OK일 때만 커밋. 한 참여자가 멈추면 전체가 잠기는 가용성 문제로 MSA에선 거의 쓰지 않는다. → Saga를 선택하는 배경 지식.

## 3. 메시징과 정합성

**Transactional Outbox**
"DB 커밋은 됐는데 Kafka 발행 직전에 서버가 죽으면?" 문제의 해법. 이벤트를 Kafka로 바로 쏘지 않고 같은 DB 트랜잭션 안에서 outbox 테이블에 INSERT한 뒤, 별도 프로세스가 outbox를 읽어 발행한다. DB 커밋과 이벤트 발행이 사실상 원자적이 된다. → 각 서비스의 outbox 테이블.

**멱등성 (Idempotency)**
같은 요청을 몇 번 반복해도 결과가 한 번 실행한 것과 같은 성질. 수학의 |x| 절댓값처럼 — 몇 번 적용해도 같다. → 멱등키(idempotency_key)로 중복 주문 방지, eventId로 중복 이벤트 처리 방지.

**멱등 컨슈머 / Inbox 패턴**
Kafka는 같은 메시지를 두 번 줄 수 있으므로(at-least-once), 컨슈머가 처리한 eventId를 테이블에 기록해두고 이미 본 이벤트는 무시하는 패턴. → processed_events 테이블.

**at-least-once (최소 1회 전달)**
메시지가 유실되지는 않지만 중복될 수 있다는 전달 보장 수준. "정확히 1회"는 비용이 커서, 보통 at-least-once + 멱등 컨슈머 조합으로 사실상의 정확히 1회를 만든다.

**DLQ (Dead Letter Queue)**
재시도를 다 해도 처리에 실패한 메시지를 격리해두는 별도 큐. 죽은 편지 보관소. 실패 메시지가 전체 처리를 막는 것을 방지하고, 나중에 원인 분석·재처리한다. → order.events.dlq, payment.events.dlq.

**백오프 (Backoff)**
재시도 간격을 점점 늘리는 전략. 지수 백오프 = 1초 → 2초 → 4초 → 8초. 장애 난 상대를 재시도 폭탄으로 더 괴롭히지 않기 위함. → 결제 타임아웃 재시도 (event-design §2.3).

**파티션 키 (Partition Key)**
Kafka 토픽은 여러 파티션으로 나뉘고, 같은 키의 메시지는 같은 파티션에 들어가 순서가 보장된다. → orderId를 키로 써서 "같은 주문의 이벤트는 순서대로 처리됨"을 보장 (토픽 설계 §4).

**이벤트 봉투 (Envelope)**
모든 이벤트가 공통으로 갖는 겉포장 — eventId, 타입, 발생 시각, 버전 등. 내용물(payload)과 분리해 일관된 처리를 가능케 한다. → event-design §5.

**correlationId**
하나의 비즈니스 흐름(주문 한 건의 여정)에 속한 모든 이벤트·로그를 묶는 추적용 ID. → 분산 트레이싱과 연결해 "이 주문이 어디까지 갔나"를 추적.

**CDC (Change Data Capture)**
DB의 변경 로그를 실시간으로 읽어 다른 시스템으로 흘리는 기술(대표 도구: Debezium). → Outbox 테이블을 읽는 방법 중 하나 (폴링 vs CDC, Phase 2에서 선택).

## 4. 데이터와 동시성

**낙관적 락 (Optimistic Lock)**
"충돌은 드물 것"이라 낙관하고 잠그지 않은 채 진행, 저장 시점에 version 컬럼으로 충돌을 감지해 실패시키는 방식. 충돌이 드물 때 유리. → orders.version, inventory.version.

**비관적 락 (Pessimistic Lock)**
"충돌이 날 것"이라 비관하고 읽는 시점부터 행을 잠그는 방식(SELECT ... FOR UPDATE). 확실하지만 대기가 생긴다. → 재고 차감 실험 후보 (ADR 후보 #8).

**append-only**
데이터를 수정(UPDATE)·삭제하지 않고 추가(INSERT)만 하는 방식. 회계 장부 원칙 — 틀린 기록은 지우지 않고 상쇄 기록을 새로 적는다. → 환불 = 음수 정산 레코드 INSERT (ERD §3).

**대사 (對査, Reconciliation)**
두 장부를 맞춰보는 일. 우리 기록과 PG사 거래내역을 대조해 누락·금액 불일치를 찾는다. 금융권·결제 도메인의 핵심 일과. → reconciliation_results 테이블, 일배치.

**귀속일 (settlement_date)**
이 거래가 "어느 날짜의 정산에 속하는가". 결제 시각과 다를 수 있어서(자정 직전 결제 등) 별도 컬럼으로 관리한다.

## 5. 운영

**관측 가능성 (Observability)**
로그·메트릭·트레이스를 통해 시스템 내부 상태를 밖에서 추론할 수 있는 능력. 모니터링(아는 문제 감시)보다 넓은 개념(모르는 문제도 조사 가능).

**분산 트레이싱 (Distributed Tracing)**
요청 하나가 여러 서비스를 거치는 전 여정을 하나의 흐름으로 추적하는 기술. → OTel(OpenTelemetry)로 게이트웨이 → Kafka → 배치까지 트레이스 연결 (Phase 4).

**TPS / p99**
TPS = 초당 처리 건수. p99 = 응답시간 상위 1% 경계값 — "요청의 99%는 이 시간 안에 응답했다". 평균은 착시가 있어서(느린 1%가 묻힘) 성능은 보통 p99로 말한다. → Phase 5 부하테스트 지표.

**카오스 엔지니어링 (Chaos Engineering)**
일부러 장애(서버 강제 종료 등)를 일으켜 시스템의 복원력을 검증하는 기법. → Phase 5 장애 시나리오 실험.
